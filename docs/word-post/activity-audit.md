# Activity audit and uplift recommendations

9 September 2026 · audit baseline `a521dea7`. The assessment below records that baseline; implementation progress is recorded at the end of this document.

Reviewed the five existing activity families, flashcard tools, vocabulary/phrasebook entry points and their relationship to the new learner player. Inspected the running local screens, saved examples, templates, route handlers, services and JavaScript. Two database queries ran read-only to verify the duplicate story title and saved writing responses. No answers were submitted, material generated, rewards awarded or records edited. Provider failure paths below are code findings, not live failure tests; this is not a child usability study.

## Assessment

The useful learning mechanics are already here. The recurring problem is that creation forms, stored records, active practice and feedback are presented together, with database-oriented labels and different save/load rules in each activity. The shared colours and fonts improve appearance, but do not resolve that structure.

Use one experience across activities: **choose or resume → practise → understand feedback → continue or finish**. Keep the current mechanics, simplify their presentation and make persistence dependable. Story work can resume after this cleanup. Native flashcards remain the next new learning capability, rather than a prerequisite for correcting existing games.

## Saved content: make it a browser, then a disclosure

The proposed toggle should be an **expand/collapse control**, not an on/off setting.

- **Before choosing an activity:** show saved content openly, with a clear empty state and a secondary Create action. Returning learners should not need to discover a hidden library.
- **While practising:** collapse it into **Saved stories (8)** or **Change story**. Expanding it must preserve the current answer. Loading another activity should handle an unsaved draft explicitly.
- **A saved item:** a human title, a short preview, and only useful metadata. For the inspected story, a proposed editorial title is **Anna and Max**, with **Beginner · 5 questions** and an audio indicator if the asset is available. This is a proposed rename, not an existing title or a migration already applied.
- **As the library grows:** search, topic/level filters and recent use; paginate larger collections. Do not call something “In progress” without the learner-specific attempt state to support it. Repeated excerpts do not prove duplicate content, so do not delete apparent duplicates automatically.

Reuse a shared saved-item view model and Jinja component for stories, games, writing and lessons. Keep `id` and `href` internal; expose `display_title`, preview, human-readable metadata and genuine activity state. Match known historical title suffixes carefully rather than stripping arbitrary parenthesised text. Format dates in the UI language, and preserve meaningful values in storage.

Use native disclosure semantics where practical, or a keyboard-operable control with accurate expanded state. [W3C disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/).

## Shared engineering uplift

**Keep Flask, Jinja/HTMX and bounded Preact interactions.** The issue is unclear responsibility and inconsistent contracts, not the inability of the stack to present a polished application.

1. **One activity layout:** title/objective, optional material, current task, response, feedback and next action. Use the existing palette/type/paper details; keep reading surfaces quiet. Give creation controls, saved content and advanced settings secondary places. Do not force every mechanic into identical tiles or a narrative wrapper.
2. **One renderer per region:** Jinja owns the shell and forms; Preact owns only explicitly mounted interactive regions. Consolidate loading and teardown in the active shell. `WordJumble.js`, `Lesson.js` and `Writing.js` appear unreferenced by the current templates/shell; verify before retiring them rather than maintaining parallel implementations. Legacy Preact/HTMX/Bootstrap still load from CDNs while the new UI is bundled: move assets toward the existing local build incrementally.
3. **Predictable routes and fragments:** move writing/lesson/jumble handlers out of `app.py` as those activities are improved. Share full-page/fragment rendering, validation and structured errors. Return escaped templates or structured data instead of interpolated HTML containing learner/provider text; reading and lesson marking contain direct interpolation today.
4. **Save, assess and reward separately:** an unfinished answer must survive provider failure and navigation. Use approved content IDs/versions and per-learner attempts instead of posting whole task definitions back as hidden-field authority. Migrate through the existing shared learning service. Legacy reward behaviour is not uniform: sentence rewards have a keyed path, story marking/saving has separate reward flags, and the remaining activities do not all use the shared policy. Do not advertise identical coins across them until adapters enforce that contract.
5. **A failure is not a score:** comprehension catches some assessment failures and returns zero scores. Show “Feedback unavailable—your answer is saved” only after the save succeeds; allow a retry with the same logical submission. Validate score ranges/rubrics, keep technical error details out of the exercise and avoid a failed optional audio/image step blocking learning.
6. **Consistent language and accessibility:** interface text follows the chosen UI language; Russian learning material remains Russian with correct language markers. Restore semantic spacing, keyboard access, focus after swaps and readable status messages. Announce save/check outcomes without unnecessarily moving focus. [W3C status-message guidance](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

## Recommended implementation order

| Order | Scope | Relative effort |
|---|---|---|
| **1. Correctness batch** | Story title/metadata display and direct links; score denominator; writing resume/full-text assessment; unique fragment/input IDs; broken Phrasebook destination; translation-direction copy | Mostly small focused fixes; navigation and grading need regression checks |
| **2. Reading as the reference activity** | Shared saved-content disclosure, clear library/creation split, focused reader and question flow, accessible word help, retained answers | Medium; proves the reusable pattern on the user's current pain point |
| **3. Apply the pattern to games** | Composition and translation first, then writing and lessons; preserve their distinct mechanics and advanced adult options | Medium per activity; do not combine all into one large rewrite |
| **4. Complete shared learner integration** | Approved versions, independent attempts/drafts, consistent assessment state and reward events for each adapter; native FSRS continues under its existing requirements | Larger; presentation changes alone cannot provide this |
| **5. Resume the story** | Compose dependable activities into Barsik's chapters | After one complete learn/save/resume/feedback loop is reliable |

Each corrected activity should pass a small practical gate: direct URL and refresh work; a saved answer reappears; a fresh attempt is explicitly fresh; retries do not duplicate saves/rewards; unavailable assessment preserves the answer without inventing a grade; library switching does not silently discard work; keyboard and narrow-screen use work. Test those behaviours, rather than snapshotting colours or asserting CSS class names.
